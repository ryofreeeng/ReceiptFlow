# ReceiptFlow 手順書

## 環境情報
- 言語：Python
- 認証：Google Drive API（OAuth2.0）
- OCR：PaddleOCR（ローカル実行・`ocr.py` の `OCR_ENGINE` 定数で切り替え可能。EasyOCRも残存）
- 仕分け：キーワードベースのルール抽出（`extract.py`・`config.toml` で品目キーワードを設定）
- Excel出力：openpyxl

---

## Step 0：Google Cloud Consoleの設定（初回のみ）

このアプリはGoogle Drive APIを使用するため、**使用者それぞれが自分のGoogleアカウントで credentials.json を発行する必要がある**。credentials.json はGitリポジトリには含まれていないため、以下の手順で取得する。

### 0-1. Googleプロジェクトを作成する

1. [Google Cloud Console](https://console.cloud.google.com/) にアクセスしてGoogleアカウントでログイン
2. 画面上部の「プロジェクトを選択」→「新しいプロジェクト」をクリック
3. プロジェクト名を入力（例：`ReceiptFlow`）して「作成」

### 0-2. Google Drive APIを有効化する

1. 左メニュー「APIとサービス」→「ライブラリ」
2. 検索欄に「Google Drive API」と入力して選択
3. 「有効にする」をクリック

### 0-3. OAuth同意画面を設定する

1. 左メニュー「APIとサービス」→「OAuth同意画面」
2. User Typeは「外部」を選択して「作成」
3. アプリ名・サポートメール・開発者のメールアドレスを入力して「保存して次へ」
4. スコープの追加画面はスキップして「保存して次へ」
5. テストユーザーに自分のGoogleアカウントのメールアドレスを追加して「保存して次へ」

> **注意**：同意画面は「テスト中」のままでよい。本番公開するとGoogleの審査が必要になる。

### 0-4. OAuthクライアントIDを作成する

1. 左メニュー「APIとサービス」→「認証情報」
2. 「認証情報を作成」→「OAuthクライアントID」
3. アプリケーションの種類：「デスクトップアプリ」を選択
4. 名前を入力して「作成」
5. 「JSONをダウンロード」をクリック
6. ダウンロードされたファイルを `credentials.json` にリネームして、このプロジェクトのルートフォルダに配置する

```
ReceiptFlow/
├── credentials.json   ← ここに置く（gitに上げない・.gitignore済み）
├── .env
├── pipeline.py
...
```

## Step 1：環境構築

### 1-1. ライブラリのインストール

```bash
cd ReceiptFlowのフォルダ
pip install -r requirements.txt
```

### 1-2. .envファイルの作成

`.env.example` をコピーして `.env` を作成し、実際のフォルダIDを記入する。

```bash
cp .env.example .env
```

`.env` の中身：
```
# Drive の unprocessed フォルダのID（PDFダウンロード元）
UNPROCESSED_FOLDER_ID=（DriveのunprocessedフォルダのURLの末尾IDを貼り付ける）

# Drive の processed フォルダのID（処理済みPDFの移動先）
PROCESSED_FOLDER_ID=（DriveのprocessedフォルダのURLの末尾IDを貼り付ける）

# Drive の renamed フォルダのID（日付リネーム済みPDFのアップロード先）
RENAMED_FOLDER_ID=（DriveのrenamedフォルダのURLの末尾IDを貼り付ける）
```

フォルダIDはDriveでフォルダを開いたときのURLの末尾：
```
https://drive.google.com/drive/folders/★ここ★
```

Drive に `unprocessed`・`processed`・`renamed` の3つのフォルダを作成してそれぞれのIDを取得する。

### 1-3. フォルダ構成の確認

```
ReceiptFlow/
├── receipts/
│   ├── unprocessed/   ← Adobe ScanのPDFを置く場所
│   ├── intermediate/  ← OCR結果テキストの一時保存先（自動生成）
│   ├── processed/     ← 処理済みに移動される場所
│   └── renamed/       ← 購入日付でリネームしたPDFの保存先（自動生成）
├── logs/              ← 実行ログの保存先（自動生成）
├── output/            ← Excel出力先
├── config.toml        ← 勘定科目・要チェック店舗・品目キーワードなど（gitに上げてよい）
├── credentials.json   ← Google Cloud Consoleからダウンロード済み（gitに上げない）
├── .env               ← フォルダIDなどの個人設定（gitに上げない）
├── .env.example       ← .envのテンプレート（gitに上げる）
├── requirements.txt
├── pipeline.py          ← 全処理のオーケストレーター（通常はこれを実行する）
├── drive_connection.py  ← DriveからPDFをダウンロードする
├── ocr.py               ← PDFからテキストを抽出する
├── extract.py           ← OCRテキストから情報を抽出してExcelに書き出す
└── docs/
    ├── 手順書.md（このファイル）
    ├── drive_connection_guide.md
    ├── ocr_guide.md
    └── extract_guide.md
```

## Step 2：Google Drive API 接続テスト

### 2-1. テストスクリプトの実行

```bash
python drive_connection.py
```

```
  ...
```

`token.json` が自動生成されているため、ブラウザは開かずにそのまま接続される。

## Step 3：OCR（PDFからテキスト抽出）

### 3-1. 前提条件

- `receipts/unprocessed/` にPDFが1件以上ある状態にする
  - 手動でフォルダにコピーするか、`python drive_connection.py` でDriveからダウンロードする

### 3-2. スクリプトの実行

```bash
python ocr.py
```

### 3-3. 初回実行時の注意

初回はPaddleOCRが複数の認識モデルをダウンロードするため、**数分〜十数分かかる**（合計数百MB）。

```
PaddleOCRを初期化中...
Creating model: ('PP-OCRv5_server_det', None, None)
...
```

と表示されたまましばらく待つ。2回目以降はキャッシュを使うため速い。

また、以下の警告は**無視して問題ない**（動作に影響しない）：

```
UserWarning: No ccache found.   ← C++コンパイルキャッシュが未インストールなだけ。無視可
```

### 3-4. 成功時の出力例

```
PaddleOCRを初期化中...

2件のPDFを処理します...

処理中: receipt_20250526.pdf
  1ページを画像に変換しました
  ページ 1 をOCR中...

--- receipt_20250526.pdf の抽出テキスト ---
〇〇スーパー
2025年05月26日
お茶        108円
弁当        540円
合計        648円
----------------------------------------
```

### 3-5. OCRエンジンの切り替え

`ocr.py` の `OCR_ENGINE` 定数を変えるだけで切り替えられる：

```python
OCR_ENGINE = "paddleocr"   # 現在のデフォルト（精度高め）
# OCR_ENGINE = "easyocr"   # 検証済み・精度不足のため不採用（下記参照）
# OCR_ENGINE = "manga-ocr" # 検証済み・領収証には不向き（下記参照）
```

### 3-5-a. EasyOCR の検証経緯（PaddleOCR に切り替えた理由）

最初は EasyOCR を使用し、以下の設定を変えながら精度を検証した。

| 検証した設定 | 内容 |
|---|---|
| ZOOM | 1.0 → 4.0 → 8.0 と段階的に上げた |
| グレースケール変換 | オン・オフで比較 |
| 2値化（threshold=240） | オン・オフで比較 |
| ノイズ除去（強度=3） | オン・オフで比較 |

**検証結果**：`zoom8.0_gray_bin240_dn3`（ZOOM=8.0 ＋ グレースケール ＋ 2値化 ＋ ノイズ除去）が人間の目で見た画質として最善だったが、OCR で認識できるテキストの精度は改善しなかった。

**結論**：EasyOCR はエンジン自体の精度に限界があり、感熱紙の領収証（文字が細かい・かすれがある）には不向き。設定のチューニングで改善できる余地がなかったため PaddleOCR に切り替えた。

### 3-5-b. manga-ocr の検証経緯（不採用の理由）

PaddleOCR に切り替えた後、日本語特化モデルとして manga-ocr も試した。

**検証結果**：ほぼ読み取れない怪文書レベルの出力になった。

**原因**：manga-ocr は漫画の**吹き出し1コマ分**を入力として想定しているモデルで、テキスト検出（どこに文字があるかの判定）を行わない。領収証1ページ全体をそのまま渡すと、複数行・表形式のテキストを「1つのテキストブロック」として無理やり読もうとするため、意味不明な出力になる。

**結論**：manga-ocr は領収証全ページ入力には不向き。コードには実装済みで切り替え可能な状態に残してあるが、現時点では使用しない。

### 3-5-c. 行マージ後処理（PaddleOCR の改行問題への対処）

PaddleOCR の検出モデルが1行を複数の領域に分割することがあり、余計な改行が出力に混入する問題があった。`dt_polys`（検出座標）を使って同じ行のテキストを連結する後処理を実装した。

```python
POSTPROCESS_MERGE_LINES = True   # Trueで行マージを有効にする（PaddleOCR使用時のみ）
MERGE_LINE_THRESHOLD = 0.5       # 行判定の閾値（平均ボックス高さの何倍まで同じ行とみなすか）
```

値を上げると判定が緩くなり（離れた領域も同じ行とみなす）、下げると厳しくなる。

### 3-6. ZOOM と前処理の設定

**ZOOM**（画像解像度の倍率）：

```python
ZOOM = 2.0  # PaddleOCR では 2.0 を推奨
            # 4.0 まで上限（5.0 以上で内部リサイズが発生）だが、4.0 にすると処理時間が大幅に増加する
            # EasyOCR 時の 8.0 より低くてよい（PaddleOCRが内部で補正するため）
```

**前処理フラグ**（PaddleOCR 使用時は全オフ確定）：

```python
PREPROCESS_GRAYSCALE = False  # PaddleOCRは自分で前処理するためオフ
PREPROCESS_BINARIZE  = False  # 2値化するとモデルが使う濃淡情報が消え精度が落ちる（検証済み）
PREPROCESS_DENOISE   = False  # 前処理はやるほど精度が下がることを確認済み
```

> **検証結果**：前処理フラグをオンにしていくほど認識精度が落ちることを実際に確認した。PaddleOCR（深層学習モデル）には前処理を一切行わず自然な画像をそのまま渡すのが最善。

## Step 4：情報抽出・Excel出力

### 4-1. 前提条件

- Step 3 の OCR を実行し、`receipts/intermediate/` にセッションフォルダが生成されている状態にする  
  （セッションフォルダ例：`receipts/intermediate/20250526-143022/`）

### 4-2. 設定ファイルの確認

`config.toml` で動作をカスタマイズできる：

```toml
debit_account = "消耗品費"
credit_account = "事業主借"
check_stores = ["〇〇スーパー", "100均"]
item_keywords = ["はちみつ", "バター"]
item_max = 2
item_exclude_words = ["割引", "%", "レジ袋"]
sort_mode = "new_only"
```

| キー | 説明 |
|---|---|
| `debit_account` | 仕訳の借方科目（例：消耗品費・食料品費） |
| `credit_account` | 仕訳の貸方科目（例：事業主借） |
| `check_stores` | この店名が含まれるレシートは「要確認」とマークされる（部分一致） |
| `item_keywords` | 摘要欄に優先採用する品目名キーワード（部分一致） |
| `item_max` | 摘要欄に採用する品目の最大件数 |
| `item_exclude_words` | 品目から除外するワード（割引・袋代など） |
| `sort_mode` | Excel出力時の並び替え方式（`"new_only"` または `"all"`） |

### 4-3. スクリプトの実行

```bash
python extract.py
```

実行するとセッション選択画面が表示される：

```
処理するセッションを選択してください：
  1: 20250526_143022
  2: 20250527_091011
番号を入力: 1

選択されたセッション: 20250526_143022

3件のテキストを読み込みました。

処理中: receipt_001.txt
  日付:     2025-05-26
  摘要:     卵、生クリームなど
  合計金額: 1580
  要チェック: False
...

出力完了: output/対面領収証の帳簿_20250526-143055記帳.xlsx
```

### 4-4. 出力ファイルの確認

`output/対面領収証の帳簿_yyyymmdd-HHmmss記帳.xlsx` が生成される。列構成：

| 列 | 内容 |
|---|---|
| 日付 | レシートから抽出した日付 |
| 摘要 | 品目名（最大2件）を「卵、生クリーム等」の形式で |
| 借方科目 | `config.toml` の `debit_account` |
| 借方金額 | 合計金額 |
| 貸方科目 | `config.toml` の `credit_account` |
| 貸方金額 | 合計金額（借方と同じ） |
| 要チェック | `check_stores` に合致した場合は `要確認`、それ以外は空白 |

> **詳しい仕組みは** `docs/extract_guide.md` を参照。
